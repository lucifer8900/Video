## 3. 完整对话时间线

### 3.1 初始想法

用户提出：

> 希望开发一款发布到 Steam 平台的视频互动游戏。用户可以通过界面点击和视频中的人物交互。游戏中的视频场景和后续发展由 AI 实时演算，以达到和玩家交互的目的。用户会提前提交大量故事设定，也就是大量小说文本，由 AI 分析并记录到数据库作为基础。

助手分析：

- 这是一个跨多个系统的大项目，不是单一功能。
- 至少包含：
  - Steam 游戏客户端。
  - AI 叙事引擎。
  - 知识库和数据库。
  - 视频生成/播放系统。
  - 成本、审核和内容安全系统。
- 第一版不建议完全实时生成所有视频。
- 推荐先考虑“预制视频片段 + AI 叙事决策 + 少量动态生成”的方案。

用户选择第一版更接近：

> A. 互动影像游戏。大量视频提前制作好，AI 主要负责选择分支、生成对白和角色反应。

助手解释：

- AI 可以在制作阶段提前演算分支。
- 用户把通过审核的分支做成预置内容。
- 玩家反馈可以先归类为有限意图，例如相信、怀疑、追问、威胁、安慰、沉默。
- AI 不直接决定最终成品，AI 帮助推演和扩写；最终进入游戏的是经过制作和质检的固定分支。

### 3.2 真人影视感和幻想奇观

用户表示：

> 偏向真人互动影像，希望有酷炫打斗、每秒的风景、幻想物种、甚至星球级幻想场景。

助手最初提出“真人拍摄 + VFX”的可能性。

用户纠正：

> 不能用真人动作捕捉，希望所有视频都由 AI 生成。

最终确认：

- 所有视频都希望由 AI 生成。
- 风格仍然是“真人影视感”。
- 不使用真人拍摄，不使用动作捕捉。
- 可以使用 AI 视频生成服务、AI 图像服务、VFX 风格的 AI 资产管线。

助手建议：

- 第一版采用“离线 AI 生成分支视频”为主。
- 中期可以做“模块化 AI 视频库”。
- 长期目标才考虑“实时完整视频生成”。

### 3.3 实时生成关键剧情视频

用户提出：

> 希望有一部分视频可以实时生成，例如根据玩家前面的操作和选择，动态生成一些关键剧情视频。这样能不能离线做到？还是必须在线服务器生成后传输到游戏客户端？

助手回答：

- 如果只是把玩家状态归类，然后提前生成对应视频，可以离线实现。
- 如果视频真的根据每个玩家独特历史生成，就需要运行时生成。
- 商业 Steam 版本更建议服务器生成，而不是客户端本地生成。

原因：

- 本地生成高质量视频对显卡、显存和模型体积要求高。
- 不能把第三方 AI API key 放在客户端。
- 视频生成需要排队、失败重试、审核、转码、存储和分发。
- Steam 对运行时 AI 内容有披露和防护要求。

推荐架构：

```mermaid
flowchart LR
  A["Steam 客户端<br/>玩家存档和选择"] --> B["游戏服务器<br/>鉴权/排队/限额"]
  B --> C["剧情引擎<br/>知识库和角色状态"]
  C --> D["生成分镜/提示词"]
  D --> E["AI 视频生成服务"]
  E --> F["审核/转码/压缩"]
  F --> G["对象存储/CDN"]
  G --> H["客户端下载并缓存"]
```

推荐第一版：

- 主线和高频分支离线预生成。
- 少量关键剧情在线生成。
- 生成结果缓存，相似状态可复用。
- 在线生成只用于章节结尾、命运转折、关键战斗、角色关系爆发等节点。

### 3.4 服务端配置

用户提出：

> 如果购买并接入 Google AI 视频生成服务，同时接入 OpenAI 的 Image 2 服务，需要服务端转发客户端请求，并将生成的视频压缩后发送到客户端。服务器需要什么配置？

助手回答：

- 如果 Google/OpenAI 负责托管模型推理，自己的服务器第一版不需要 GPU。
- 服务器主要负责任务编排、转码、存储、CDN、成本限流和鉴权。

推荐 MVP 配置：

```text
API 服务器：2 vCPU / 4GB RAM
Worker 服务器：2-4 vCPU / 8-16GB RAM
数据库：托管 PostgreSQL
队列：Redis 或托管队列
存储：GCS / S3 / R2
分发：CDN + 短期签名 URL
转码：CPU + FFmpeg 起步
```

关键建议：

- 不要让 API 服务器直接传大视频。
- 视频生成后放对象存储/CDN。
- API 只返回任务状态和短期签名下载 URL。
- 加玩家限流、章节限流、每日预算上限。

提到的外部服务和文档参考：

- Google Veo 文档中有视频长度、分辨率、输出格式等限制。
- OpenAI 图像生成适合做角色定妆、关键帧、场景概念图，再给视频模型做图生视频。
- Steamworks 内容问卷要求说明运行时 AI 内容和防护措施。

### 3.5 语音输入和剧情判断

用户提出：

> 希望不止提供固定选项，还希望游戏接入语音输入，能读取用户说的话，给 AI 分析，然后决定后续剧情怎么走。

助手建议：

```text
玩家自由说话 -> 语音转文字 -> 意图分析 -> 安全/越界检查 -> 剧情状态机 -> 选择分支或生成关键视频
```

核心原则：

- 玩家可以自由表达。
- 系统内部不能让自由文本无限改写剧情。
- 应把语音压缩成结构化意图。

示例：

```json
{
  "intent": "distrust_and_probe",
  "tone": "cautious",
  "target": "npc_a",
  "topic": "ruins_entrance",
  "branch_id": "ask_secret_path",
  "confidence": 0.86
}
```

用户之后选择：

> 语音等级希望是高级。语音会影响剧情判断、角色关系，也会触发隐藏分支。

助手将语音系统拆成：

- 即时对话层：让 NPC 能回应。
- 剧情裁决层：提取意图、语气、承诺、威胁、谎言、线索和隐藏触发条件。

高级语音结构：

```json
  "discovered_secret": "npc_a_false_identity",
  "relationship_delta": {
    "trust": -8,

  },
  "hidden_branch_candidate": "expose_npc_origin",
  "confidence": 0.91
}
```

### 3.6 NPC 回应和真人影视场景

用户提出：

> 希望游戏里的场景都是真人影视场景，尽量没有静态图，或者非常非常少。

用户选择：

> A 和 B 的结合。NPC 的回应短视频可以提前生成，放到游戏里面循环调用。

助手确认方向：

- 全视频真人影视感互动游戏。
- 普通 NPC 互动用预生成短视频循环 + AI 语音/字幕 + 剧情状态判断。
- 关键节点再播放或生成专属剧情视频。
- 静态图只用于菜单、档案页、加载页或极少量辅助场景。

随后用户进一步纠正：

> NPC 口型肯定要对应。玩家虽然说不同的话，但实际意思可以分析出来，然后对应多个场景，根据每个场景生成对应短视频。

最终确定：

- 不是用任意循环视频匹配实时台词。
- 玩家语音进入后，系统识别为有限剧情意图。
- 每个意图有预先确定的 NPC 台词。
- 视频生成阶段按这些台词生成有口型短视频。
- 运行时只做语义匹配和变体选择。

示例：

```text
玩家说法 A：“你不说入口在哪，我不会相信你。”
玩家说法 B：“别绕圈子，把遗迹入口告诉我。”
玩家说法 C：“我知道你在隐瞒入口，说出来。”
```

都归类为：

```json
{
  "intent": "probe_ruins_entrance",
  "tone": "distrustful"
}
```

播放：


### 3.8 剧情编译器、玩家方案矩阵和视频生成顺序

用户提出三条关键修正：

1. AI 提取剧情后，要在所有需要玩家选择的地方分析，归纳出玩家所有可能方案，然后生成对应 NPC 处理方案。这些方案都要符合剧情总线，并能合理嵌入。
2. 视频生成要在剧情处理完之后，而不是提前生成视频。
3. 玩家游玩剧情时可以自由行动，例如经过大地图风景点去看看，探索山间是否有机缘，或者锄强扶弱，以及其他大地图随机剧情。

助手确认这是核心设计变更：

- 从“视频分支播放器”升级为“剧情编译器 + 玩家方案矩阵 + 视频资产生成计划 + 大地图开放事件层”。

正确顺序：

```mermaid
flowchart LR
  A["小说文本"] --> B["AI剧情分析"]
  B --> C["主线/支线/任务/时效"]
  C --> D["玩家可能方案归纳"]
  D --> E["NPC处理方案"]
  E --> F["审核是否符合剧情总线"]
  F --> G["锁定场景与分支"]
  G --> H["生成对应真人影视视频"]
  H --> I["游戏运行时播放/少量在线生成"]
```

大地图自由行动层：

- 风景点探索。
- 山间机缘。
- 路见不平。
- 随机遭遇。
- 支线线索。
- 资源和奇遇。

建议采用“受控开放大地图”：

- 事件来自文本解析出的地点、势力、人物、传说、冲突和事件池。
- AI 负责匹配、变体和后果裁决。
- 不能破坏剧情总线。

### 3.9 增量更新、离线版和离线语音

用户提出：

1. 程序更新要支持增量更新，不能每次更新都重新安装。
2. 要支持离线版本，默认没有动态视频生成和 NPC 对话功能。
3. 离线版本能不能支持语音识别和匹配？

助手回答：

- Steam 本身支持 SteamPipe 增量更新。
- 视频类游戏要注意资源拆包。

建议 depot/内容包拆分：

```text
Base Client Depot
Chapter_01_Videos
Chapter_02_Videos
OpenWorld_Region_A_Videos
Language_CN_Audio_Subtitles
Optional_Offline_ASR_Model
Optional_HighRes_Video_Pack
```

离线基础版支持：

- 播放预生成真人影视视频。
- 主线/支线固定分支。
- 本地任务状态机。
- 本地大地图事件池。
- 本地存档。
- 固定选项。
- 可选本地语音识别和意图匹配。

离线基础版不支持：

- 云端动态视频生成。
- 开放式 NPC 云端长对话。
- 云端大模型剧情推演。
- 云端生成新支线。

离线语音识别：

```text
本地语音识别 -> 本地意图匹配 -> 播放已有视频分支
```

可选档位：

- 关键词/短语匹配。
- 本地语音转文字 + 场景意图匹配。
- 本地小模型语义理解。

### 3.10 固定选项 + 可选语音输入

用户提出最终交互修正：

> 语音识别也应该是可选。应该在剧情节点给出几个选项让玩家选择，同时提供一个语音输入。玩家可以自己说话。如果玩家辱骂 NPC、说不相干内容、错误语音、输入太久，对应 NPC 都应该有不同应对反应。比如直接走、发怒打玩家一顿、或别的操作，具体根据剧情文本判断。

最终确认：

- 固定选项是基础。
- 语音输入是可选高级入口。
- 异常语音不是错误弹窗，而是剧情行为。

输入分类：

```text
有效意图：进入对应剧情分支
辱骂/挑衅：NPC 发怒、降低关系、开战或离开
不相干：NPC 困惑、追问、无视
错误识别：要求玩家重说或走兜底
说太久：NPC 打断、不耐烦、默认推进或触发时效
沉默超时：NPC 离开、任务时间推进或默认分支
```

```json
{

    "insult": "npc_angry_warning_or_attack",
    "irrelevant": "npc_confused_prompt",

    "too_long": "npc_interrupts",

  }
```

   - 展示主线/支线/时效任务的混合场景结构。

9. `text-to-quest-approaches.html`
   - 对比文本剧情到任务系统的三种自动化程度：

     - 受控动态推演。
     - 完全动态故事模拟。
   - 推荐第一版用 AI 提取 + 人工审核。

10. `narrative-compiler-open-world.html`
    - 展示剧情编译后再生成视频。
    - 包含玩家方案归纳、NPC 处理方案、人工审核、大地图自由事件层。

11. `offline-online-update-architecture.html`
    - 展示离线基础版 + 在线 AI 增强 + 增量内容更新。
    - 区分离线能做什么、在线增强做什么。

12. `choice-plus-optional-voice.html`
    - 展示剧情节点固定选项 + 可选语音输入。
    - 异常语音进入 NPC 剧情反应，而不是普通错误。

## 5. 最终需求状态

截至本会话末尾，当前产品方向为：

1. 目标平台：Steam。
2. 类型：AI 真人影视互动游戏。
3. 视频来源：全部视频尽量由 AI 生成，不使用真人拍摄或动作捕捉。
4. 画面风格：真人影视感，尽量不用静态图。
5. 内容来源：用户提供大量小说文本。
6. 核心内容管线：小说文本 -> AI 剧情分析 -> 玩家方案矩阵 -> NPC 处理方案 -> 人工审核 -> 视频生成计划 -> AI 视频生成。
7. 游戏结构：主线 + 支线 + 大地图自由事件。
8. 场景结构：混合式。
9. 任务时效：混合式，由剧情文本判断。
10. 交互方式：固定选项为基础，可选语音输入为高级入口。
11. 语音功能：在线高级语义理解，离线可选 ASR + 意图匹配。
12. NPC 回应：根据玩家语义归类，播放对应有口型短视频。
13. 异常输入：辱骂、跑题、错误识别、说太久、沉默都进入 NPC 剧情反应。
14. 动态视频：第一版只在少量关键剧情节点在线生成。
15. 离线版本：默认完整可玩，但没有动态视频生成和开放式云端 NPC 对话。
16. 更新策略：SteamPipe 增量更新，视频资源按章节/区域/语言/清晰度拆包。

## 6. 建议第一版 MVP 范围

为了验证闭环，第一版不要直接做完整大世界。建议：

- 一个主线章节。
- 一个可探索大地图区域。
- 2-4 个主要剧情场景。
- 少量支线任务。
- 1 组大地图随机事件池。
- 若干 NPC，数量由剧情决定，不预设固定数字。
- 每个关键节点提供固定选项和可选语音。
- 每个场景建立玩家意图矩阵。
- 每个意图生成 NPC 有口型回应短视频。
- 离线版可完整跑通。
- 在线版只增加少量关键视频动态生成。

## 7. 待决策问题

下一轮开发前需要继续确认：

- 第一章使用哪一段小说文本。
- 游戏引擎选择：Unity、Unreal、Godot 或 Web/自研壳。
- 叙事编译器先做编辑器工具，还是先做服务端后台。
- 视频生成供应商：Google Veo、OpenAI 视频/图像、其他模型或组合。
- OpenAI 图像生成用于定妆图、关键帧、场景参考还是直接游戏资产。
- 离线 ASR 方案：whisper.cpp、Vosk、系统语音识别或其他。
- 大地图表现形式：影视节点地图、2D 地图、3D 区域或混合。
- 存档设计：是否允许回溯、是否支持多分支存档。
- 视频包体预算：720p、1080p、高分辨率可选包如何拆。
- 在线生成成本上限：每玩家每日、每章节、每账号如何限制。

## 8. 技术模块建议

后续可以拆成以下模块：

1. `Narrative Compiler`
   - 读取小说文本。
   - 抽取角色、地点、阵营、任务、事件。
   - 识别需要玩家选择的位置。
   - 生成玩家方案矩阵和 NPC 处理方案。

2. `Story State Machine`
   - 管理主线、支线、任务时效、世界状态、关系值、线索和隐藏分支。

3. `Interaction Node Runtime`
   - 渲染固定选项。
   - 接收可选语音。
   - 做意图匹配和异常输入分类。
   - 选择对应视频。

4. `Video Asset Planner`
   - 根据剧情矩阵生成视频资产清单。
   - 输出台词、镜头、角色、场景、情绪、分辨率和标签。

5. `Online AI Service`
   - 云端语义理解。
   - 动态关键视频生成。
   - 生成任务排队。
   - 审核、转码、CDN 分发。

6. `Offline Runtime`
   - 本地任务状态机。
   - 本地视频分支。
   - 本地可选语音识别和意图匹配。

7. `Patch/Depot Strategy`
   - 基础程序和视频包拆分。
   - 按章节、区域、语言、清晰度和离线 ASR 模型拆包。

## 10. 不要丢掉的关键原则

- AI 可以辅助编剧和推演，但主线核心真相必须可控。
- 视频生成必须在剧情处理和分支矩阵锁定后进行。
- 玩家可以自由说话，但系统要把语音归类为受控意图或异常输入。
- NPC 异常反应也是剧情内容。
- 失败、超时和错过任务也要继续推进世界，而不是简单重试。
- 离线版必须完整可玩。
- 在线 AI 只是增强层，不能成为游戏启动和基础通关的硬依赖。
- 不要把 API key 放到客户端。
- 不要把大视频从 API 服务器直接转发给客户端。
- 不要把 `.superpowers/` 临时目录提交到 Git。
